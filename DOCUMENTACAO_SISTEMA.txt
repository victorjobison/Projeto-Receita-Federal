DOCUMENTACAO DO SISTEMA PROSPECCAO B2B

Este arquivo explica a organizacao do projeto, arquivo por arquivo, e mostra como as funcionalidades se conectam de forma logica.


1. VISAO GERAL

O sistema e uma aplicacao web Flask organizada no padrao MVC.

MVC significa:

- Model: arquivos que conversam com o banco de dados.
- View: telas HTML exibidas para o usuario.
- Controller: arquivos que recebem as rotas, tratam formularios e chamam os services.

Neste projeto tambem existe uma camada Service:

- Service: regras de negocio. Ela fica entre o Controller e o Model.

Fluxo comum:

Usuario acessa uma tela
-> Controller recebe a requisicao
-> Service aplica a regra de negocio
-> Model consulta ou grava no PostgreSQL
-> Controller devolve uma View HTML ou resposta JSON

5. PASTA prospeccao_b2b

Esta e a pasta principal da aplicacao.
E nela que ficam o Flask, as regras de negocio, o acesso ao banco e as telas.


prospeccao_b2b/app.py

Arquivo de entrada do sistema.
Ele importa create_app de app_factory.py, cria a aplicacao Flask e roda o servidor quando executado diretamente.

Quando voce executa:

python app.py

e este arquivo que inicia o sistema.


prospeccao_b2b/app_factory.py

Cria e configura a aplicacao Flask.

Responsabilidades:

- carregar configuracoes do config.py
- registrar os controllers/blueprints
- carregar o usuario logado antes de cada requisicao

Controllers registrados:

- auth_bp
- company_bp
- lead_bp
- admin_bp


prospeccao_b2b/config.py

Centraliza configuracoes do sistema.

Le variaveis do arquivo .env, como:

- DB_HOST
- DB_PORT
- DB_NAME
- DB_USER
- DB_PASSWORD
- FLASK_SECRET
- BRASILAPI_URL
- PAGE_SIZE
- ADMIN_EMAIL
- ADMIN_PASSWORD
- JWT_SECRET
- JWT_ALGORITHM

Assim o codigo nao precisa ter senha ou configuracao fixa dentro dos arquivos Python.


prospeccao_b2b/db.py

Centraliza a conexao com PostgreSQL usando psycopg.

Funcoes principais:

- get_conn: abre conexao com o banco
- fetch_one: executa SELECT e retorna um unico registro
- fetch_all: executa SELECT e retorna varios registros
- execute: executa INSERT, UPDATE ou DELETE
- execute_script: executa scripts SQL inteiros, usado no init_db.py

Este arquivo evita repetir codigo de conexao em todos os models.


prospeccao_b2b/init_db.py

Inicializa o banco de dados.

Quando voce roda:

python init_db.py

ele faz:

1. cria a aplicacao Flask
2. le o arquivo schema.sql
3. cria as tabelas no PostgreSQL
4. verifica se o admin inicial existe
5. cria o admin inicial se ainda nao existir

O admin inicial vem do .env:

- ADMIN_EMAIL
- ADMIN_PASSWORD


prospeccao_b2b/schema.sql

Schema usado diretamente pela aplicacao ao rodar init_db.py.

Ele cria as mesmas tabelas principais:

- usuarios
- empresas
- leads
- interacoes
- password_reset_tokens
- refresh_tokens

Este e o arquivo de schema mais importante para execucao da aplicacao.


prospeccao_b2b/requirements.txt

Dependencias necessarias para rodar a aplicacao.

Principais pacotes:

- Flask: framework web
- psycopg[binary]: conexao PostgreSQL
- requests: chamada para BrasilAPI
- python-dotenv: leitura do .env
- bcrypt: hash de senhas
- python-jose: criacao de JWT


prospeccao_b2b/.env

Arquivo local de configuracao.
Nao deve ser enviado para repositorio publico.

Contem dados reais do ambiente, como senha do banco e segredo da aplicacao.


prospeccao_b2b/.env.example

Modelo de configuracao.
Serve para mostrar quais variaveis o sistema precisa.

Ao configurar em outra maquina, copie para .env e ajuste os valores.

12. FUNCIONALIDADES DO SISTEMA POR FLUXO

12.1 Login

1. Usuario acessa /login.
2. auth_controller recebe e-mail e senha.
3. AuthService.authenticate valida os dados.
4. UserModel.find_by_email busca usuario.
5. verify_password compara senha com hash bcrypt.
6. Se estiver correto, user_id e salvo na sessao.
7. Usuario entra no sistema.


12.2 Logout

1. Usuario clica em Sair.
2. auth_controller limpa a sessao.
3. Usuario volta para /login.


12.3 Consulta de CNPJ

1. Usuario informa CNPJ na tela inicial.
2. company_controller chama CompanyService.consultar_cnpj.
3. O service limpa e valida o CNPJ.
4. O service chama BrasilAPI.
5. CompanyModel.upsert_from_api salva ou atualiza a empresa no PostgreSQL.
6. Usuario volta para a listagem de empresas.


12.4 Filtro de empresas

1. Usuario preenche filtros na tela inicial.
2. company_controller monta dicionario de filtros.
3. CompanyService chama CompanyModel.list_filtered.
4. O model monta SQL com filtros.
5. A tela exibe as empresas encontradas.


12.5 Criar lead

1. Usuario clica em Adicionar lead.
2. company_controller chama LeadService.criar_lead.
3. LeadService verifica se a empresa existe.
4. LeadModel.create cria registro na tabela leads.
5. Lead aparece no funil do consultor.


12.6 Listar leads

1. Usuario acessa /leads.
2. lead_controller chama LeadModel.list_filtered.
3. Se for CONSULTOR, filtra apenas leads dele.
4. Se for ADMIN, pode ver todos e filtrar por consultor.
5. Tela lista os leads.


12.7 Atualizar status do lead

1. Usuario abre detalhe do lead.
2. Escolhe novo status.
3. lead_controller chama LeadService.atualizar_status.
4. LeadService valida permissao e status.
5. LeadModel.update_status grava no banco.


12.8 Registrar interacao

1. Usuario abre detalhe do lead.
2. Informa tipo e descricao.
3. lead_controller valida acesso ao lead.
4. InteractionModel.create grava no banco.
5. Historico aparece na tela.


12.9 Editar interacao

1. Usuario edita uma interacao.
2. InteractionModel.update tenta atualizar.
3. O SQL so permite se data_interacao for menor ou igual a 24 horas.
4. Se passou de 24 horas, a edicao nao acontece.


12.10 Excluir interacao

1. Somente ADMIN ve a opcao de excluir.
2. admin_required protege a rota.
3. InteractionModel.delete remove o registro.


12.11 Cadastrar consultor

1. ADMIN acessa /admin/consultores.
2. Preenche nome, e-mail, senha e perfil.
3. AdminService.criar_consultor gera hash da senha.
4. UserModel.create grava usuario.


12.12 Relatorio global

1. ADMIN acessa /admin/relatorio.
2. AdminService.relatorio_global chama LeadModel.report_by_consultor_status.
3. O sistema agrupa leads por consultor e status.
4. A tela exibe os totais.


12.13 Recuperacao de senha

1. Usuario acessa Esqueci minha senha.
2. Informa e-mail.
3. AuthService.request_password_reset gera token.
4. PasswordResetModel.create salva token com validade de 1 hora.
5. Usuario acessa link gerado.
6. AuthService.reset_password valida token.
7. UserModel.update_password grava nova senha com bcrypt.
8. Token e marcado como usado.


12.14 JWT e refresh token

Rotas API:

- /api/auth/login
- /api/auth/refresh
- /api/auth/revoke

Fluxo:

1. Cliente envia e-mail e senha para /api/auth/login.
2. Sistema retorna access_token e refresh_token.
3. Quando access_token expira, cliente envia refresh_token para /api/auth/refresh.
4. Sistema retorna novo access_token.
5. Cliente pode revogar refresh_token em /api/auth/revoke.

14. OBSERVACOES IMPORTANTES

- Nao edite arquivos dentro de __pycache__. Eles sao gerados automaticamente pelo Python.
- O arquivo .env contem dados sensiveis e nao deve ser publicado.
- Sempre rode init_db.py antes de iniciar o sistema pela primeira vez.
- A aplicacao principal esta em prospeccao_b2b/app.py.
- O padrao MVC ajuda a manter cada responsabilidade no lugar certo:
  Controller recebe requisicao.
  Service aplica regra.
  Model acessa banco.
  Template exibe tela.
